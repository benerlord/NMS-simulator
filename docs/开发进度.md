### LEGACY-04 SQL 执行器强制外包 LIMIT/OFFSET，缺少分页旁路开关（2026-05-02 记录）
- **现象**：`backend/app/core/sql_executor.py:71-83` 的 `_build_paged_sqls` 对**所有** SQL 都强制外包一层 `SELECT * FROM (<用户 SQL>) _t LIMIT :__limit__ OFFSET :__offset__`，并自动绑定 `__limit__ = pageSize`、`__offset__ = (page-1)*pageSize`。无法关闭。
- **影响范围**：
  1. 调用方使用 `offset + limit` 风格分页（如 ManageOne / OpenStack）时，用户在 SQL 里手写 `LIMIT :limit OFFSET :offset` 会和外层叠加，造成"双重分页"——只能用"把外层 `defaultPageSize` 调到 1000 兜底"的 workaround
  2. 详情接口（按 ID 取一行）、聚合接口（COUNT / SUM）也被强制分页，需要靠 `LIMIT 1` + 默认 page=1 凑出来
  3. 非 SQLite 占位符语义（即 `:name` 不能参与算术）让用户难以在 SQL 内自行表达 `(:pageNo - 1) * :pageSize`，进一步暴露此短板
- **未做原因**：M2-M5 期所有验收用例都按 page-based 分页设计，没暴露此场景；本次会话由用户提"想用 `:pageSize * (:pageNo - 1)` 算 OFFSET"触发讨论后才识别出
- **建议方案（后续版本）**：
  1. `config.pagination` 增加 `enabled?: boolean`（默认 true，向后兼容）
  2. `_build_paged_sqls` 增加 `paginate=True` 参数，`False` 时返回 `(None, "<prefix><cleaned>")`，跳过外层包装
  3. `execute_paged` 在 `paginate=False` 时跳过 count 查询，`total = len(items)`，`page=1` `pageSize=len(items)`
  4. 前端 `ApiConfigModal` 在分页配置区加一个"启用框架分页"开关；关闭后参数名输入框置灰
  5. e2e 测试覆盖三条路径：
     - 默认 enabled=true，行为同现状
     - enabled=false + 用户 SQL 写 `LIMIT :limit OFFSET :offset` → 不被外层裁切
     - enabled=false + 用户 SQL 不写 LIMIT → 全表返回（注意性能上限，建议加防御性 `LIMIT 10000`）
- **优先级**：中（场景 B/C/D 真实存在，目前的 workaround 不优雅但未阻塞；建议安排在下一期一起做）
- **预计工作量**：0.5-1 天（含 sql_executor 改动 + 前端开关 + e2e）
- **关联讨论**：本次会话 2026-05-02，用户问"分页接口在 SQL 里写 `:pageSize * (:pageNo - 1)`" 与"其他接口不用 pageNo/pageSize 怎么写 SQL"两轮触发

### 后端校验：新增 step 3.5

`request_pipeline.py` 在 step 3（auth）之后、step 4（fault）之前插入 `_step3_5_validate_request(ctx)`：

**执行顺序理由**：缺 token → 401（不让看），带 token 但参数缺 → 400（让看才能告诉它怎么改）。符合最小信息泄露原则。

**校验逻辑**：

```python
async def _step3_5_validate_request(ctx):
    req = ctx.detail.config.get("request") or {}
    if not req:
        return                                           # 未声明则放过（向后兼容）

    declared_headers = {h["name"].lower() for h in req.get("headers", [])}
    declared_query = {p["name"] for p in req.get("query", [])}

    # 1. 声明字段必填 / expectValue 校验
    for h in req.get("headers", []):
        v = ctx.request.headers.get(h["name"])
        if h.get("required") and v is None:
            raise PipelineError(400, 40020, f"缺少请求头 {h['name']}")
        if h.get("expectValue") and v is not None and v != h["expectValue"]:
            raise PipelineError(400, 40021, f"请求头 {h['name']} 不匹配预期值")

    for p in req.get("query", []):
        v = ctx.request.query_params.get(p["name"])
        if p.get("required") and v is None:
            raise PipelineError(400, 40022, f"缺少 query 参数 {p['name']}")
        if v is not None and p["type"] != "string":
            try:
                _coerce(v, p["type"])
            except ValueError:
                raise PipelineError(400, 40023, f"query {p['name']} 类型应为 {p['type']}")

    # 2. 严格模式：未声明字段拒绝
    for q_name in ctx.request.query_params.keys():
        if q_name not in declared_query:
            raise PipelineError(400, 40025, f"未声明的 query 参数: {q_name}")
    # 注意：headers 不做严格白名单（HTTP 标准头如 Host/Accept/User-Agent 太多，
    # 严格模式只对"声明了但不允许"的反向语义没意义；只校验声明字段是否合规即可）

    # 3. body 必填校验
    body_spec = req.get("body")
    if body_spec and body_spec.get("required"):
        raw = await ctx.request.body()
        if not raw:
            raise PipelineError(400, 40026, "请求体不得为空")
```

**错误码分配**：
- `40020` 缺少必填请求头
- `40021` 请求头值不匹配
- `40022` 缺少必填 query 参数
- `40023` query 参数类型错误
- `40024` （**预留给 LEGACY-02 content-type 校验**，HTTP 415）
- `40025` 未声明的 query 参数（严格模式拒绝）
- `40026` 请求体必填但为空
- `40027`-`40029` 预留

**严格模式细化决策**：
- query：严格白名单，未声明字段 → 40025
- headers：**不**做严格白名单（HTTP 标准头如 `User-Agent` / `Accept` / `Connection` 等浏览器/curl 自动注入，强制白名单会使所有调用都失败）。只校验声明字段的存在性与 expectValue
- body：本期不做 schema 校验（example 仅文档展示），只看 required 是否为空
