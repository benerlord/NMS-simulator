# 大规模拓扑性能压测 — 设计方案

## 1. 场景定义

| 维度 | 目标规模 | 当前上限（已验证） |
|------|---------|------------------|
| 节点类型数 | 10 ~ 30 种 | 11（种子） |
| 单类型节点数 | 1 万 ~ 10 万 | 3 万（M4-03 基准） |
| 总节点数 | 10 万 ~ 100 万 | 3 万 |
| 总边数 | 30 万 ~ 300 万 | 3 万 |
| 边关系复杂度 | 多对多、跨类型、含约束 | 简单 |
| 并发采集请求 | 100 ~ 1000 QPS | 单请求测试 |

---

## 2. 当前架构瓶颈分析

### 2.1 数据库层（SQLite）

| 瓶颈点 | 现状 | 万级+ 表现 |
|--------|------|-----------|
| 单文件写入锁 | WAL 模式，读写可并发但写串行 | 多采集插件同时写入时排队，延迟线性增长 |
| CTE 视图生成 | 每种节点类型动态拼接视图 SQL | 30 种类型 × 10 万行 → CTE 展开后 SQL 达数 MB，解析耗时 |
| 无连接池 | 每次 `connect()` 新建 sqlite3 连接 | 高并发下文件打开/关闭开销显著 |
| 全表扫描风险 | 某些查询缺少覆盖索引 | `SELECT * FROM nodes WHERE topology_id=? AND node_type_id=?` 已有索引，但跨类型聚合查询可能扫描 |
| 内存限制 | SQLite 进程内，受单进程内存约束 | 100 万节点 × (attrs 3 条 × 200B) ≈ 600MB，接近 Python 进程合理上限 |

**可承受上限**（经验估值）：单 SQLite 文件在 WAL + NORMAL sync 下，~50 万节点 + ~100 万边仍可工作，但 CI/CTE 查询需优化。

### 2.2 API 层

| 瓶颈点 | 现状 | 问题 |
|--------|------|------|
| `/graph` 全量加载 | 一次性返回全部 nodes + edges + canvas | 100 万实体 → JSON 数十 MB，序列化/传输/前端解析三杀 |
| 列表无分页 | `GET /node-types` 等返回全量 | 影响小（类型数量少），但 nodes/edges 列表在 M4-03 已补分页 |
| 同步阻塞 | FastAPI 同步 endpoint + `connect()` | 大查询阻塞事件循环；M4-03 已关注 |

### 2.3 画布渲染层（AntV X6）

| 瓶颈点 | 现状 | 问题 |
|--------|------|------|
| 全量渲染 | `resetCells(cells)` 一次性创建所有 Node/Edge 对象 | 1 万+ 节点 → 浏览器卡死（每个 Node 是一个 DOM + SVG 元素） |
| 无视口裁剪 | 画布外的节点照样渲染 | 大量不可见元素浪费 GPU/CPU |
| 无 LOD | 所有节点同等细节 | 缩小到全局视角时每个节点文本仍然渲染 |

**可承受上限**：AntV X6 纯 SVG 模式下约 **500 ~ 1000 个节点**体验可接受；超过需虚拟化或降级。

### 2.4 采集模拟（Mock 管道）

| 瓶颈点 | 现状 | 问题 |
|--------|------|------|
| SQL 执行器 | `execute_paged` 对 CTE 视图做 `SELECT * FROM view LIMIT ? OFFSET ?` | 外层 LIMIT 不会下推到 CTE 内部，数据库先生成全量结果集再截断 |
| 响应模板 | `render_template` 逐字段渲染 | 大数据量时模板变量替换 O(n) |
| 请求日志 | 每次请求 `INSERT INTO request_logs` | 高 QPS 写入竞争 |

## 3. 分阶段设计方案

### 阶段 1：大规模数据生成能力（基础）

**目标**：能快速生成 10 万 ~ 100 万级别的拓扑数据用于压测。

#### 3.1.1 批量数据生成器

新增独立脚本 `test_scripts/bench_data_gen.py`，不走 HTTP，直接写 SQLite：

```
python test_scripts/bench_data_gen.py \
  --topology    perf-bench-100k \
  --node-types  switch,router,server,firewall,port,vm,ecs,hypervisor,pod,container,app \
  --per-type    10000 \
  --edges-per-node 3 \
  --output      backend/data/bench_100k.db
```

**关键设计**：

- **模板化节点生成**：每种类型定义 `{nameTemplate, dnTemplate, attrGenerators}`，如 `switch-{i}`、`pod-{namespace}-{i}`
- **批量 INSERT**：`executemany` 在单个事务内，每 5000 条一批
  - 10 万节点 ≈ 3~5 秒（SQLite 纯插入）
  - 100 万节点 ≈ 30~60 秒
- **边生成策略**：可配置多种拓扑模型
  - `star`：中心节点辐射
  - `chain`：链式连接
  - `random`：随机配对（可限制跨类型）
  - `layered`：三层架构（access→aggregation→core）
- **可重复**：固定 seed 保证相同参数每次生成一致拓扑

#### 3.1.2 数据类型定义

```python
# bench_data_gen.py 内置
NODE_TYPE_TEMPLATES = {
    "switch": {
        "category": "physical",
        "render_mode": "none",
        "name_fmt": "SW-{site}-{idx:05d}",
        "attrs": {"vendor": ["Huawei","Cisco","H3C"], "model": "CE6800", "ip": "10.{a}.{b}.{c}"},
        "edges_out": {"router": 2, "server": 48},  # 每种目标类型建多少边
    },
    # ... 其他类型
}
```

### 阶段 2：后端性能优化

#### 2.2.1 图数据分块加载

将 `/graph` 端点拆分为：

```
GET /admin/api/topologies/{id}/summary       → { nodeCount, edgeCount, typeCounts, ... }
GET /admin/api/topologies/{id}/nodes-page    → 分页节点 + canvas 坐标（viewport-aware）
GET /admin/api/topologies/{id}/edges-page    → 分页边
GET /admin/api/topologies/{id}/neighbors/{nodeId} → 展开节点的邻居子图
```

**viewport-aware 加载**：前端传 `?x=0&y=0&w=1920&h=1080&zoom=1.0`，后端仅返回当前视口内的节点 + 画布坐标。

#### 2.2.2 SQL 优化

| 优化项 | 方案 | 效果 |
|--------|------|------|
| CTE 下推 | 对 `execute_paged` 的 SQL 做 AST 重写，将 `LIMIT/OFFSET` 注入 CTE 内部 | 100 万行 → 只扫描 50 行 |
| 物化视图（临时表） | 采集时先 `CREATE TEMP TABLE _collect_switch AS SELECT ...`，再从中分页 | 避免每次请求重建 CTE |
| 连接池 | 使用 `sqlite3.Connection` 单例 + 线程锁，或 `aiosqlite` + 连接复用 | 减少连接创建开销 |
| 读写分离 | 采集读请求走 WAL 只读连接（`sqlite3_open_v2` + `SQLITE_OPEN_READONLY`），管理写走主连接 | 读不阻塞写 |

#### 2.2.3 异步化

将同步 `def` endpoint 改为 `async def` + `aiosqlite` / `run_in_executor`：

```python
@router.get("/topologies/{id}/nodes-page")
async def list_nodes_page(id: str, page: int = 1, ...):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(_executor, _sync_list_nodes, id, page, ...)
```

用 `ThreadPoolExecutor(max_workers=4)` 专门处理 SQL 查询，避免阻塞事件循环。

### 阶段 3：前端画布虚拟化

#### 3.3.1 视口裁剪

```
┌──────────────────────────────────┐
│ 浏览器视口 (1920×1080)            │
│  ┌──────────┐                    │
│  │ 可见节点  │    ← 仅渲染视口内   │
│  │ ~200 个   │       节点+边      │
│  └──────────┘                    │
│  视口外 → 不创建 DOM/SVG          │
└──────────────────────────────────┘
        ↓ zoom out (缩小)
┌──────────────────────────────────┐
│ 可见 ~10km×10km 范围              │
│ → LOD 降级：节点变成色块，隐藏文本  │
│ → 聚合：相近节点合并为一个聚合点    │
└──────────────────────────────────┘
```

**实现方案**：

1. 监听 `graph.transform` 事件获取当前视口矩阵
2. 反算视口覆盖的 world rect
3. 通过空间索引（R-Tree / 网格哈希）快速查询视口内节点
4. 视口内节点 → `graph.addNode`；视口外 → `node.remove()` 但保留数据
5. 平移/缩放时增量更新

AntV X6 **不原生支持视口裁剪**（它是全量 SVG）。两个路径：

- **路径 A（轻量）**：仍在 Vue 层控制——在 `TopologyCanvas.vue` 维护一个 `visibleNodeIds` Set，`watch` 视口变化后通过 `graph.getNodes()` 遍历，对比可见集合并 `node.setVisible(true/false)`。X6 的 `setVisible` 会移除/添加 DOM 元素。
- **路径 B（彻底）**：大规模场景下切换到 Canvas 渲染（`@antv/x6` 支持 Canvas 模式但功能弱于 SVG），或采用 `@antv/g6`（GPU 加速的 Canvas 图可视化引擎，专为大规模设计），但需重写渲染层。

**推荐阶段 3 采用路径 A**，改动最小，预期可支撑 5000~10000 节点流畅交互。

#### 3.3.2 层级细节（LOD）

| 缩放级别 | 节点表现 | 边表现 |
|---------|---------|-------|
| > 80% | 完整渲染：名称 + 图标 + 状态 + 属性 Tooltip | 样式 + 箭头 |
| 40% ~ 80% | 简化：名称 + 色块 | 直线 |
| 10% ~ 40% | 色块 8×8px | 不渲染 |
| < 10% | 类型聚合点（"交换机 × 500"） | 不渲染 |

#### 3.3.3 渐进式加载

首屏加载 → 仅加载图概要（`summary`），画布为空白 + 类型计数叠加层。
用户缩放/平移 → 按需按视口加载节点分页，类似地图瓦片。

### 阶段 4：采集性能压测框架

#### 4.1 压测工具选型

| 工具 | 适用场景 | 优势 |
|------|---------|------|
| `locust` | HTTP 级别压测，模拟并发采集请求 | Python 原生，可定义复杂用户行为 |
| 自定义脚本 | DB 级别压测（绕过 HTTP） | 控制更细粒度 |

推荐 `locust` + 自定义客户端。

#### 4.2 压测场景定义

```python
# test_scripts/bench_collection.py  (locustfile)
from locust import HttpUser, task, between

class CollectorUser(HttpUser):
    wait_time = between(0.5, 2.0)

    @task(3)
    def collect_all_switches(self):
        """采集所有交换机——分页遍历"""
        self.client.get("/mock/v1/switches?page=1&pageSize=100")

    @task(2)
    def collect_pod_with_containers(self):
        """采集 Pod → 容器关联查询"""
        self.client.get("/mock/v1/pod-containers?podId=xxx")

    @task(1)
    def collect_full_inventory(self):
        """全量采集——大 SQL 查询"""
        self.client.get("/mock/v1/inventory/full")
```

#### 4.3 性能指标

| 指标 | 目标（10 万节点） | 目标（100 万节点） |
|------|-----------------|------------------|
| 分页查询 P50 | < 200ms | < 500ms |
| 分页查询 P99 | < 1s | < 3s |
| 图数据加载（首屏） | < 2s | < 5s |
| 画布平移帧率 | > 30 fps | > 20 fps |
| 并发 100 QPS 下 P99 | < 2s | < 5s |
| DB 文件大小 | < 500MB | < 3GB |

## 5. 数据库替代方案（如 SQLite 不够用）

| 方案 | 适用规模 | 优势 | 代价 |
|------|---------|------|------|
| **DuckDB** | 100 万 ~ 1000 万 | 分析型查询快 10~100×，兼容 SQLite 语法，单文件部署 | 并发写不如 SQLite，需额外依赖 |
| **PostgreSQL** | > 100 万 + 高并发写 | 成熟、并发优秀、支持连接池 | 需要独立服务进程，部署复杂度升 |
| **SQLite + 分片** | 多拓扑分文件 | 保持简单，每拓扑一个 `.db` 文件 | 跨拓扑查询需应用层聚合 |

**推荐**：先走到 Phase 3（50 万级），DuckDB 作为 Phase 4 的平滑升级路径——它支持直接 attach SQLite 文件、SQL 方言高度兼容，迁移成本最低。

## 6. 推荐实施顺序

| 优先级 | 任务 | 说明 |
|--------|------|------|
| P0 | 数据生成器（阶段 1） | 没有数据就无法压测，这是所有后续工作的前提 |
| P1 | `/summary` + 分页图 API（阶段 2.2.1） | 让大图至少可以被"加载"而不炸内存 |
| P1 | 视口裁剪（阶段 3 路径 A） | 让大图在画布上可交互 |
| P2 | SQL CTE 下推优化（阶段 2.2.2） | 提升采集查询性能 |
| P2 | Locust 压测脚本（阶段 4） | 可量化性能瓶颈 |
| P3 | LOD 降级（阶段 3.3.2） | 体验优化 |
| P3 | 异步化（阶段 2.2.3） | 高并发采集场景 |
| P4 | DuckDB 迁移评估 | 当 SQLite 确实到极限时 |

## 7. 已知风险

1. **AntV X6 SVG 模式上限**：经社区验证，3000+ 节点时交互明显卡顿。视口裁剪可将可感知上限推到 ~1 万，但如果真实场景需要同时展示 5 万+ 节点，需评估迁移到 `@antv/g6` 或 `Cytoscape.js`（Canvas 渲染）
2. **SQLite WAL 写并发**：WAL 模式下多读单写。如果采集场景需要每秒 100+ 个并行写事务，SQLite 会成为瓶颈——此场景建议直接上 PostgreSQL
3. **内存**：100 万节点带 3 属性 → 约 600MB 磁盘、~1.2GB 加载到 Python dict。单个 FastAPI 进程需至少 2GB 内存
