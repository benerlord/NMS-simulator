# 节点组方案 — 分析评估

## 方案回顾

用户提出的"节点组"概念：

- 一个节点组 = 同一节点类型 × N 个节点（如"交换机 × 10000"）
- 创建时指定：数量、属性生成策略（固定 / 随机 / 递增）
- 组间连接：取模连接或其他方式（如组 A 的每 5 个节点连 1 个组 B 的节点）

---

## 结论：方案可行，但有两条实现路径，选哪条是关键

核心分歧在于：**节点组在运行时是"虚"还是"实"？**

---

## 路径 A：虚拟节点组（运行时保持为组，不展开）

```
存储                         运行时
┌──────────────────┐       ┌──────────────────┐
│ node_groups 表    │       │ API 查询时        │
│ id: grp_switch_01 │       │ 动态计算虚拟节点   │
│ node_type: switch │  ──→  │ 范围 [0, 9999]    │
│ count: 10000      │       │                    │
│ attr_rules: {...} │       │ 按需生成属性值      │
│ edge_rules: {...} │       └──────────────────┘
└──────────────────┘
```

### 优势

1. **存储极小**：10 万节点 → 10 行组记录 + 10 行边规则记录
2. **创建即时**：INSERT 几行就完成，无需等待批量写入
3. **修改方便**：改一条 `attr_rules` JSON，10 万节点的属性全变
4. **边建模优雅**：组间边以规则表达，天然适合描述"每台交换机连 48 台服务器"这种拓扑规律
5. **可嵌套**：组内可以嵌套子组（"每个 Pod 含 3 个容器"）

### 缺陷（致命级）

1. **无法表示个体差异**：第 5037 个交换机离线了？虚拟模型做不到——要么全在线，要么全离线。真实采集中，设备状态、属性值必然有个体差异
2. **无法做单节点操作**：点击画布上的某个节点→它的 id 是 `grp_switch_01#5037`，你无法对它单独修改、拖拽、标注
3. **SQL 查询困难**：`SELECT * FROM virtual_nodes WHERE id = 'grp_switch_01#5037'` 不成立。现有 SQL 采集管道完全依赖 `nodes` 实体表，全部需要重写
4. **画布渲染不兼容**：AntV X6 只能渲染具体的 Node 对象。即使前端展开了 10000 个虚拟节点，展开后的节点没有独立 id，画布交互全部失效
5. **边不可见**：前端需要实际的 `source_id → target_id` 来画线。规则描述的边如果不展开，浏览器什么都画不出来
6. **与现有系统冲突**：当前 14 张表、6-step pipeline、CTE 视图生成——全链路基于实体节点。虚拟方案相当于另起炉灶

**路径 A 判决**：❌ **不推荐**。它与现有架构完全冲突，且在"个体差异"这一核心需求上有不可弥补的缺陷。

## 路径 B：物化节点组（创建时展开为真实节点，组仅作为管理单元）

```
创建时                             运行时
┌──────────────────┐            ┌──────────────────┐
│ 用户定义节点组     │            │ nodes 表          │
│ 类型: switch      │  展开写入   │ node_00001 ~      │
│ 数量: 10000       │  ────────→  │ node_10000        │
│ 命名: SW-{i:05d}  │            │ (标准实体节点)     │
│ ip:   10.0.{i%256}.│           │                    │
│        {i/256}    │            │ node_groups 表     │
│                   │            │ (记录归属关系)     │
└──────────────────┘            └──────────────────┘
```

**本质**：节点组是数据**生成时**的批量抽象，生成后节点就是普通实体，与现有系统完全兼容。

### 新增表设计

```sql
CREATE TABLE IF NOT EXISTS node_groups (
  id              TEXT PRIMARY KEY,           -- grp_xxx
  topology_id     TEXT NOT NULL,
  node_type_id    TEXT NOT NULL,
  group_name      TEXT NOT NULL,
  node_count      INTEGER NOT NULL,
  name_template   TEXT NOT NULL,              -- "SW-{site}-{i:05d}"
  attr_strategies TEXT NOT NULL,              -- JSON
  edge_strategies TEXT,                       -- JSON, nullable
  created_at      TEXT NOT NULL DEFAULT (datetime('now')),
  FOREIGN KEY (topology_id) REFERENCES topologies(id) ON DELETE CASCADE,
  FOREIGN KEY (node_type_id) REFERENCES node_types(id)
);

-- 节点表增加字段（可选，用于反向追溯）
ALTER TABLE nodes ADD COLUMN group_id TEXT;
```

### `attr_strategies` JSON 结构

```json
{
  "vendor": { "strategy": "random", "pool": ["Huawei", "Cisco", "H3C", "Arista"] },
  "ip":     { "strategy": "increment", "base": "10.0.0.1", "step": 1, "subnet": 24 },
  "model":  { "strategy": "fixed", "value": "CE6800-48S6CQ" },
  "cpu":    { "strategy": "range", "min": 4, "max": 64 },
  "version":{ "strategy": "weighted", "options": [{"v":"v2.1","w":70},{"v":"v2.2","w":30}] }
}
```

### `edge_strategies` JSON 结构

```json
{
  "target_group_id": "grp_servers",
  "edge_type_code": "physical_link",
  "mode": "modulo",
  "modulo_n": 48,
  "direction": "outgoing"
}
```

支持模式：

| 模式 | 描述 | 示例 |
|------|------|------|
| `modulo` | 每 N 个源节点连 1 个目标节点，循环分配 | 48 台服务器→1 台交换机端口 |
| `one_to_n` | 每个源节点连 N 个目标节点（顺序） | 1 台宿主机→10 台 VM |
| `all_to_all` | 笛卡尔积（慎用，N×M） | 全网状 BGP peer |
| `dense` | 源节点和目标节点按 index 一一配对 | server-{i} → switch-{i} |
| `layered` | 层级模式：上层每 M 个连下层每 N 个 | 经典三层网络 |

### 展开流程

```
POST /admin/api/topologies/{id}/node-groups/{groupId}/materialize
  ↓
1. 读取 node_groups 行，解析 attr_strategies / edge_strategies
2. 循环 i = 1..node_count：
   - 生成 node_id: topology_{topo_id}_{group_code}_{i:06d}
   - 渲染 name 模板
   - 按 attr_strategies 生成每条 node_attrs
   - 批量 INSERT（每 5000 条）
3. 循环 edge_strategies：
   - 按连接模式生成 (source_id, target_id) 对
   - 批量 INSERT edges
4. 返回: { materializedNodes: 10000, materializedEdges: 48000, elapsedMs: 3200 }
```

### 优势

1. **与现有系统 100% 兼容**：展开后就是普通 nodes/edges，现有查询、CTE、Canvas 渲染、mock 管道全部直接可用
2. **生成语义强大**：模板 + 策略远比手动构造丰富，且可重复
3. **保留组追溯**：`nodes.group_id` 让用户知道哪些节点来自同一个组
4. **可实现组的批量操作**：选中组 → 批量删除/导出该组全部节点
5. **可选再生成**：删掉组的所有节点 → 重新 materialize（换参数），快速迭代压测场景

### 缺陷

1. **存储仍然是实体的**：10 万个节点就是 10 万行，没有节省磁盘。这是"节点组"和"虚拟节点"的根本区别
2. **展开需要时间**：10 万节点 + 50 万边 ≈ 3~5 分钟（纯 DB 写入），不是即时的
3. **修改不灵活**：一旦展开，修改属性只能逐节点更新（或删掉重新展开）
4. **个体差异受限**：只能通过策略随机/递增生成，无法精确指定"第 5037 个的 ip 是 10.0.5.42"。对于压测场景这完全够用，但对于精确仿真不够

## 双路径对比

| 维度 | 路径 A（虚拟） | 路径 B（物化） |
|------|:--:|:--:|
| 存储大小 | ★★★★★ | ★★ |
| 创建速度 | ★★★★★ | ★★★ |
| 个体差异 | ★ | ★★★★ |
| 单节点操作 | ★ | ★★★★★ |
| 与现有架构兼容 | ★ | ★★★★★ |
| 画布渲染 | ★ | ★★★★★ |
| SQL 采集 | ★ | ★★★★★ |
| 批量修改 | ★★★★★ | ★★ |
| 适合场景 | 宏观拓扑分析 | **性能压测（本系统目标）** |

---

## 推荐：路径 B（物化节点组）作为数据生成器的高层封装

具体来说：

1. 在原 `bench_data_gen.py` 脚本之上，增加 `node_groups` 表和管理 API
2. 前端类型管理页面新增"节点组"Tab，可视化管理组定义
3. 点击"展开(materialize)" → 后端批量写入实体节点/边 → 实时返回进度（WebSocket 推送百分比）
4. 展开后的节点与手动创建的节点共存，在画布上无差别渲染
5. 画布旁增加"组筛选"面板：按组名高亮/隐藏/选择该组全部节点
6. 支持"删除组"（级联删除该组所有实体节点）

**你的方案本质是好的——问题在于"虚 vs 实"的边界**。建议走物化路径：组作为生成期的组织单元，运行时数据仍然是实体。

---

## 额外补充：你方案中的一个关键设计是正确的

"组间连接用取模"——这个思想非常好且必要。真实数据中心的很多拓扑确实是取模规律的：

- 每台 Leaf 交换机连 48 台服务器（顺序分配）
- 每台 Spine 连所有 Leaf（全互联）
- 每台宿主机连 N 台 VM（子网划分）

取模/循环/笛卡尔积 这三种模式已经可以覆盖绝大多数拓扑生成场景。建议在 edge_strategies 中优先实现这三种。
