## 2. 系统架构

### 2.1 架构总览

系统采用 **分层架构 + 插件化协议服务 + 事件驱动** 的设计，核心原则：

- **分层解耦**：表现层、接口层、业务层、数据层各司其职，层间通过接口通信
- **插件化协议**：每种协议（HTTP/SNMP/SFTP/Kafka）是独立插件，统一生命周期管理，可独立启停
- **事件驱动**：组件间通过事件总线松耦合通信，避免直接依赖
- **数据中心化**：TopologyManager 作为唯一数据源，所有协议服务从中读取数据

### 2.3 分层职责

| 层 | 职责 | 关键约束 |
|----|------|----------|
| **Presentation** | 用户交互、视图渲染 | 不包含业务逻辑，只通过 API/WS 与后端通信 |
| **API** | 路由分发、请求校验、响应序列化 | 不包含业务逻辑，仅做请求转发和格式转换 |
| **Service** | 核心业务逻辑、服务编排 | 通过 EventBus 解耦服务间通信，通过 DAL 访问数据 |
| **Protocol Plugin** | 协议服务实现 | 遵循 ProtocolPlugin 接口规范，只从 TopologyManager 读取数据 |
| **Data** | 数据存取、查询执行 | 对上层暴露统一接口，屏蔽内存/持久化差异 |

## 3. 核心模块设计

### 3.1 EventBus（事件总线）

事件总线是系统解耦的核心机制，采用进程内发布/订阅模式。

**职责：**
- 组件间异步通信，消除直接依赖
- 事件广播，一个事件可被多个消费者处理
- WebSocket 事件桥接，将内部事件转发到前端

**事件分类：**

| 事件类别 | 事件名 | 触发时机 | 典型消费者 |
|----------|--------|----------|-----------|
| 拓扑事件 | `topology.loaded` | 拓扑加载到内存 | MemoryStore、ProtocolManager |
| | `topology.changed` | 设备/端口/链路变更 | MemoryStore、WebSocket |
| | `topology.saved` | 拓扑持久化完成 | WebSocket |
| 配置事件 | `config.api.updated` | HTTP 接口配置变更 | HttpMockServer |
| | `config.protocol.updated` | 协议配置变更 | 对应协议插件 |
| 协议事件 | `protocol.started` | 协议服务启动 | WebSocket、Dashboard |
| | `protocol.stopped` | 协议服务停止 | WebSocket、Dashboard |
| | `protocol.error` | 协议服务异常 | WebSocket、Logger |
| 请求事件 | `request.received` | 收到外部请求 | RequestLogger、WebSocket |
| | `request.completed` | 请求处理完成 | RequestLogger、WebSocket |
| 告警事件 | `alarm.created` | 告警生成 | SnmpAgent(Trap)、WebSocket |
| | `alarm.cleared` | 告警清除 | SnmpAgent(Trap)、WebSocket |

**事件流转示意：**

```
用户在前端修改拓扑
       │
       ▼
  API Layer 接收请求
       │
       ▼
  TopologyManager 更新内存数据
       │
       ▼
  EventBus.emit("topology.changed", {devices: [...], ports: [...]})
       │
       ├──→ MemoryStore: 同步更新内存 SQLite 虚拟表
       ├──→ WebSocket:   推送变更通知到前端
       ├──→ HttpMockServer: 后续查询自动使用新数据（无需操作）
       └──→ SchedulerService: 重置自动保存计时器
```

### 3.2 ServiceRegistry（服务注册中心）

**职责：**
- 管理所有业务服务的实例化和生命周期
- 提供服务发现，各服务通过注册中心获取依赖
- 统一初始化和关闭顺序

**管理的服务：**

| 服务 | 依赖 | 说明 |
|------|------|------|
| `TopologyManager` | DAL, EventBus | 拓扑数据 CRUD，内存数据维护 |
| `ConfigManager` | DAL, EventBus | 接口配置和协议配置管理 |
| `SessionManager` | EventBus | Token 颁发、验证、过期管理 |
| `ProtocolManager` | EventBus, TopologyManager | 协议插件注册、启停、状态监控 |
| `SchedulerService` | EventBus, TopologyManager, DAL | 定时任务调度（自动保存、文件生成等） |
| `WebSocketManager` | EventBus | WebSocket 连接管理、事件桥接 |
| `RequestLogger` | EventBus | 请求日志记录与查询 |

**启动顺序：**

```
1. EventBus          ← 基础设施，最先启动
2. DAL               ← 数据层初始化（SQLite 文件 + 内存库）
3. TopologyManager   ← 从数据库加载拓扑到内存
4. ConfigManager     ← 加载接口/协议配置
5. SessionManager    ← 初始化 Token 存储
6. SchedulerService  ← 注册定时任务
7. ProtocolManager   ← 根据配置启动协议插件
8. WebSocketManager  ← 开始接受前端连接
```

### 3.3 TopologyManager（拓扑管理器）

系统的数据中心，所有拓扑数据的唯一所有者。

**职责：**
- 维护内存中的拓扑数据（devices / ports / links / alarms / metrics）
- 提供 CRUD 操作接口
- 维护索引（byId / byDN / byDeviceId）
- 拓扑切换、版本管理
- 数据变更时发布事件

**数据流向：**

```
TopologyManager（唯一数据源）
       │
       ├──写入──→ MemoryStore     (内存 SQLite，供 HTTP 接口 SQL 查询)
       ├──写入──→ PersistStore    (文件 SQLite，持久化保存)
       │
       ├──读取←── HttpMockServer  (通过 MemoryStore SQL 查询)
       ├──读取←── SnmpAgent       (通过 TopologyManager 接口直接读取)
       ├──读取←── SftpServer      (通过 TopologyManager 接口直接读取)
       └──读取←── KafkaProducer   (通过 TopologyManager 接口直接读取)
```

**数据同步机制：**

```
前端编辑操作
     │
     ▼
TopologyManager 更新内存对象 + 索引
     │
     ├──同步──→ MemoryStore.sync_table("devices", [...])
     │          将变更的数据同步到内存 SQLite 对应的虚拟表
     │
     └──异步──→ EventBus.emit("topology.changed")
                └──→ SchedulerService 触发防抖自动保存
                     └──→ PersistStore 写入 SQLite 文件
```

### 3.4 ProtocolManager（协议管理器）

**职责：**
- 注册和管理所有协议插件
- 统一的启动、停止、重载接口
- 监控各协议服务运行状态
- 协议配置变更时通知对应插件

**插件接口定义（抽象基类）：**

```
ProtocolPlugin (ABC)
├── name: str               插件名称标识
├── start() -> None         启动协议服务
├── stop() -> None          停止协议服务
├── restart() -> None       重启
├── reload_config() -> None 重新加载配置（不重启）
├── status() -> PluginStatus  返回运行状态
└── health_check() -> bool  健康检查
```

**插件状态机：**

```
STOPPED ──start()──→ STARTING ──成功──→ RUNNING
   ▲                               │
   │                          stop()/异常
   │                               │
   └──────────── STOPPING ◄────────┘
```

**插件注册流程：**

```
ProtocolManager.register(HttpMockServer)
ProtocolManager.register(SnmpAgent)
ProtocolManager.register(SftpServer)
ProtocolManager.register(KafkaProducer)

# 启动时根据配置决定是否自动启动
for plugin in registered_plugins:
    if config.is_enabled(plugin.name):
        await plugin.start()
```

### 3.5 DataAccessLayer（数据访问层）

**职责：**
- 对上层提供统一数据访问接口
- 管理内存存储和持久化存储
- 屏蔽 SQLite 操作细节

**双存储架构：**

| 存储 | 实现 | 用途 | 读写特征 |
|------|------|------|----------|
| **MemoryStore** | SQLite `:memory:` | HTTP 接口 SQL 查询、协议数据读取 | 高频读、写跟随拓扑变更 |
| **PersistStore** | SQLite 文件 | 拓扑持久化、配置存储、版本历史 | 低频写、启动时读 |

**MemoryStore 虚拟表同步：**

```
TopologyManager 中的 Python 对象
    devices: List[Device]
    ports: List[Port]
    links: List[Link]
    alarms: List[Alarm]
    metrics: List[Metric]
         │
         │  sync_table()
         ▼
MemoryStore (SQLite :memory:)
    DELETE FROM devices; INSERT INTO devices VALUES (...), (...), ...
    DELETE FROM ports;   INSERT INTO ports VALUES (...), (...), ...
    ...
         │
         │  execute_sql(sql, params)
         ▼
    HTTP 接口查询结果
```

同步策略：
- **全量同步**：拓扑加载/切换时
- **增量同步**：单个设备/端口/链路变更时，只更新对应记录
- **批量同步**：批量操作后统一同步

## 4. 协议插件架构

**关键设计点：**
- RouteDispatcher 维护动态路由表，监听 `config.api.updated` 事件自动更新
- Middleware Pipeline 可扩展，新增中间件只需注册，不修改已有代码
- SQL 模式通过 MemoryStore 执行查询，Static 模式直接渲染 JSON
- 请求日志通过 EventBus 发出，不直接依赖日志模块

## 5. WebSocket 实时通信

### 5.1 架构

```
┌──────────────┐         ┌───────────────┐         ┌──────────────┐
│   Frontend   │◄──WS───►│  WebSocket    │◄──sub───│   EventBus   │
│   Client     │         │  Manager      │         │              │
└──────────────┘         └───────────────┘         └──────────────┘
```

WebSocketManager 订阅 EventBus 上的事件，过滤后推送给前端。前端也可通过 WebSocket 发送命令。

### 5.2 消息协议

```json
{
  "type": "event | command | response",
  "channel": "topology | protocol | request_log | alarm",
  "action": "具体动作",
  "payload": {},
  "timestamp": "ISO8601"
}
```

### 5.3 频道划分

| 频道 | 推送内容 | 前端消费者 |
|------|----------|-----------|
| `topology` | 拓扑数据变更、保存状态 | 拓扑编辑器 |
| `protocol` | 协议服务状态变更（启动/停止/错误） | 仪表盘、协议管理页 |
| `request_log` | 实时请求日志 | 仪表盘、日志页面 |
| `alarm` | 告警新增/清除 | 数据查看页 |
| `system` | 系统级通知（自动保存完成、磁盘空间等） | 全局通知 |

## 7. 关键设计决策

### 7.1 为什么用事件总线而不是直接调用

| 场景 | 直接调用 | 事件总线 |
|------|----------|----------|
| 拓扑变更 → 同步内存表 | TopologyManager 导入 MemoryStore | TopologyManager 发事件，MemoryStore 自行订阅 |
| 拓扑变更 → 通知前端 | TopologyManager 导入 WebSocketManager | 同上 |
| 新增协议插件 | 修改 TopologyManager 代码 | 新插件自行订阅事件，零侵入 |

事件总线使得 TopologyManager 不需要知道谁在消费数据变更，新增消费者不影响已有代码。

### 7.2 为什么内存查询用 SQLite 而不是 AlaSQL

| 维度 | AlaSQL (JS) | SQLite :memory: (Python) |
|------|-------------|-------------------------|
| 语言生态 | 需要 JS 运行时 | Python 标准库自带 |
| SQL 兼容性 | 标准 SQL 子集 | 几乎完整的 SQL 标准 |
| 性能（3 万行 JOIN） | 较慢 | 极快（C 实现） |
| 维护状态 | 社区维护，更新慢 | SQLite 核心团队维护 |
| 参数绑定 | 有限 | 完整的命名参数支持 |

### 7.3 HTTP Mock Server 与管理 API 的隔离

系统存在两个 HTTP 服务，职责完全不同，必须隔离：

| | 管理 API | HTTP Mock Server |
|---|----------|-----------------|
| **用途** | 前端管理界面调用 | MindOps 插件调用 |
| **端口** | 默认 8000 | 用户可配置（如 8080） |
| **路由** | `/api/*` 固定路由 | 用户在界面配置的动态路由 |
| **生命周期** | 随应用启停 | 可独立启停 |

两者运行在不同端口，互不干扰。管理 API 是 FastAPI 主应用的一部分，Mock Server 是可插拔的协议插件。

### 7.4 扩展新协议的步骤

得益于插件化架构，新增协议只需：

1. 在 `protocols/` 下新建目录，实现 `ProtocolPlugin` 抽象基类
2. 在 `ProtocolManager` 中注册新插件
3. 订阅需要的 EventBus 事件
4. 通过 TopologyManager 读取拓扑数据

不需要修改任何已有业务代码。

```

   → 加载 SQLite 数据库
   → 加载拓扑到内存
   → 根据配置启动协议服务
```
