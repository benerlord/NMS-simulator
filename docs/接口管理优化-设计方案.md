# 接口管理优化 — 设计方案

## 问题分析

### 问题 1：接口无法导出和导入

**现状**：`api_configs` 表仅支持单条 CRUD，前端和后端均无任何批量导出/导入功能。用户在测试环境配置好一批接口后，无法迁移到另一个环境。

### 问题 2：SQL 数据源列字段格式不一致

**现状**：SQL 视图面板（`SqlViewPanel`）展示数据库列名，均为 `snake_case`（如 `device_name`、`ip_address`）。但参数映射表（`ParamMappingTable`）的 `bindTo` 字段和请求校验的字段名由用户手动输入，可能混用 `camelCase`（如 `deviceName`）。这导致：

- 用户不清楚应该用哪种格式绑定 SQL 列
- 参数名与列名不匹配时，SQL 查询结果无法正确映射
- 响应模板中的 `{{fieldName}}` 占位符格式无明确约定

### 问题 3：接口需要分类

**现状**：`group_name` 是一个自由文本字段（`VARCHAR`），前端过滤仅支持精确匹配。没有按"网管系统"或"资源类型"分组的能力。实际情况：

- 不同的网管系统（北京 NMS、上海 NMS）有各自独立的接口
- 同一网管系统内有多种资源类型（设备查询、告警管理、性能统计）
- 接口列表扁平，无法按层级浏览

### 问题 4：需要支持同一个网管系统开放多个端口实例

**现状**：`api_configs` 表没有 `port` 字段。Mock 服务只在一个端口上运行（由 `APP_PORT` 环境变量决定）。实际情况：

- 北京 NMS 可能需要在 `8081` 端口提供设备查询，`8082` 端口提供告警查询
- 上海 NMS 在 `8091` 端口提供服务
- 每个端口实例需要独立的一组接口
- 接口的 `UNIQUE(method, path)` 约束在跨端口时不再适用——不同端口可以有相同的 `GET /api/health`

---

## 设计目标

1. 接口支持 JSON 导出/导入（含嵌套 config 配置）
2. 统一 SQL 列字段引用格式为 `snake_case`
3. 接口支持二级分类（网管/设备 + 资源类型）
4. 支持多端口实例，接口按实例隔离

---

## 方案设计

### 整体思路

新增 **端口实例（mock_instance）** 作为接口的容器。端口实例绑定到网管/设备（domain），接口按实例隔离。接口分类通过 `domain_id` + `category` 二级字段实现。

```
┌──────────┐    ┌──────────────┐    ┌─────────────────┐
│  domain  │    │  topology    │    │  mock_instance  │
│          │1:N │              │1:N │                 │
│  id      │◄───│  domain_id   │◄───│  topology_id    │
│  name    │    │  id          │    │  id             │
└──────────┘    │  name        │    │  name           │
                │  ...         │    │  port           │
                └──────────────┘    │  enabled        │
                       │            └─────────────────┘
                       │ 1:N
                       ▼
                ┌──────────────┐
                │  api_configs │
                │  topology_id │
                │  method      │
                │  path        │
                │  category    │
                └──────────────┘
```

| 实体 | 含义 | 举例 |
|------|------|------|
| domain | 网管/设备环境 | "北京网管" |
| mock_instance | 一个端口实例，绑定到拓扑 | "北京-设备查询（8081）" |
| api_config | 一个 Mock 接口，绑定到拓扑 | `GET /api/devices` |

UNIQUE 约束从 `(method, path)` 改为 `(instance_id, method, path)`。

## 各问题方案详解

### 问题 1：接口导出/导入

**格式**：JSON（非 Excel）。因为 `config` 是嵌套 JSON 结构，Excel 不擅长表达。

**导出**：`POST /api-configs/export` — 按 `instance_id` 或 `ids[]` 导出，返回 JSON 文件下载。

**导入**：`POST /api-configs/import` — 上传 JSON，以 `instance_id + method + path` 匹配，新建或覆盖更新。

**JSON 格式**：
```json
{
  "schemaVersion": "1.0",
  "exportedAt": "2026-05-27T...",
  "apis": [
    {
      "name": "查询设备列表",
      "method": "GET",
      "path": "/api/devices",
      "enabled": true,
      "category": "设备查询",
      "dataSource": "sql",
      "sqlText": "SELECT * FROM topology_nodes",
      "config": { "params": [...], "response": {...}, "auth": {...} }
    }
  ]
}
```

### 问题 2：SQL 列字段格式统一

**根因**：参数映射的 `bindTo` 和请求校验的字段名由用户手动输入，没有与 SQL 列名对齐。

**方案**：

1. **约定 SQL 列引用统一使用 `snake_case`**（与数据库原生列名一致）
2. **`availableFieldNames` 改为从 SQL 执行结果自动提取**：
   - 用户写好 SQL 后，点击"测试运行"
   - 运行结果返回列名列表，自动填充到 `availableFieldNames`
   - 同时展示列名格式提示（黄色 Tag 标注"列名使用 snake_case"）
3. **响应模板中的占位符同步**：`{{column_name}}` 统一用 snake_case 列名

### 问题 3：接口分类

**方案**：以**网管/设备作为顶层目录**，接口按域分组展示，每个域目录可折叠展开。

**数据模型**：`api_configs` 表新增 `domain_id`（FK → domains）和 `category` 字段，与问题 4 的实例表解耦。

| 字段 | 类型 | 说明 |
|------|------|------|
| `domain_id` | TEXT FK → domains | 所属网管/设备（复用已有域表） |
| `category` | TEXT | 接口分类标签（可选，如"设备查询"、"告警管理"） |

**前端交互 — 目录式分组展示**：

```
┌─────────────────────────────────────────────────────────┐
│ 接口配置                                    [新建接口]   │
├─────────────────────────────────────────────────────────┤
│ 🔍 搜索接口...                                          │
├─────────────────────────────────────────────────────────┤
│ ▼ 北京网管 (12)                        [展开/折叠]      │
│   ┌───────────────────────────────────────────────────┐ │
│   │ 名称             方法  路径          分类    实例  │ │
│   │ 查询设备列表      GET   /api/devices  设备查询 8081│ │
│   │ 查询设备详情      GET   /api/device/..设备查询 8081│ │
│   │ 查询告警列表      GET   /api/alerts   告警管理 8081│ │
│   │ ...                                               │ │
│   └───────────────────────────────────────────────────┘ │
├─────────────────────────────────────────────────────────┤
│ ▶ 上海网管 (5)                                          │
├─────────────────────────────────────────────────────────┤
│ ▶ 未归类 (3)                                            │
└─────────────────────────────────────────────────────────┘
```

**关键交互**：

- 每个网管/设备对应一个可折叠目录（**默认全部折叠**），标题显示名称 + 接口数量
- **网管/设备管理页面新增一个时，接口页面自动同步出现对应目录**（即使目录内尚无接口也显示，接口数为 0）
- 展开目录后内部是一个小表格，列出该网管/设备下所有接口
- "未归类"目录收纳 `domain_id = NULL` 的旧接口
- 搜索框可跨目录过滤接口
- 点击目录标题右侧 **[+]** 按钮，快速在该网管/设备下新建接口，弹窗自动填入对应 `domain_id`，无需用户手动选择
- 点击页面顶部 **[新建接口]** 按钮（无目录上下文时），创建的接口归入"未归类"

**新建/编辑接口弹窗**：
- **不显示"所属网管/设备"下拉框** — 网管/设备归属由创建入口决定（点击哪个目录的 [+] 即属于哪个）
- 弹窗中仅保留分类下拉（预设值 + 允许自定义输入）
- 编辑接口时也不可修改网管/设备归属（如需转移，通过"移动到"操作或导出导入实现）

### 问题 4：多端口实例

**方案**：新增 `mock_instances` 表 + 实例管理页面。

**关联链路**：实例 → 拓扑 → 网管/设备。实例绑定到拓扑（而非直接绑定域），自动继承拓扑下的所有接口。

```
mock_instance ──topology_id──► topology ──domain_id──► domain
                                    │
                              api_configs (topology_id)
```

一个实例 = 在某个端口上运行某个拓扑的全部 Mock 接口。多个实例可以绑定同一拓扑（如 8081、8082 都提供"北京网管"的接口）。

**`mock_instances` 表**：
```sql
CREATE TABLE IF NOT EXISTS mock_instances (
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  topology_id     TEXT NOT NULL,
  port            INTEGER NOT NULL,
  description     TEXT,
  enabled         INTEGER NOT NULL DEFAULT 1,
  created_at      TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at      TEXT NOT NULL DEFAULT (datetime('now')),
  FOREIGN KEY (topology_id) REFERENCES topologies(id) ON DELETE CASCADE,
  UNIQUE (port)
);
```

**`api_configs` 表**：**不需新增 `instance_id` 列**。接口只通过 `topology_id` 关联拓扑。实例通过 `topology_id` 找到所有接口，无需逐接口绑定。

**为何不需要 TC4-3 / TC4-4**：
- 不同实例 = 不同端口 = 独立 FastAPI 子进程，各自注册路由
- `GET /api/health` 在端口 8081 和 9081 上是两个不同端口的端点，数据库层面不存在冲突
- DB `UNIQUE(method, path)` 约束无需修改

**实例管理页面**：新增左侧导航项"实例管理"，用户可：

- 创建/编辑/删除实例
- 为实例指定拓扑（topology），自动继承拓扑下的所有接口
- 查看实例的端口、所属拓扑、拓扑下接口数
- 一键启用/禁用实例

### 运行时进程管理（InstanceRunner）

**当前状态**：`mock_instances` 表仅为配置元数据，所有接口注册在主进程的 `APP_PORT`（默认 8080）上。实例端口尚未启动独立服务。

**目标**：启用实例后，自动在对应端口启动子进程，仅暴露该实例拓扑下的接口。禁用/删除实例时停止子进程。

#### 架构

```
┌──────────────────────────────────────────────────┐
│  主进程 (8080)                                    │
│  ┌────────────┐  ┌─────────────────────────────┐ │
│  │ Admin API  │  │ InstanceRunner (进程管理器)  │ │
│  │ (CRUD)     │  │ - 读取 mock_instances        │ │
│  │            │  │ - 启动/停止子进程             │ │
│  │            │  │ - 健康检查 + 自动重启         │ │
│  └────────────┘  └─────────────────────────────┘ │
└──────────────────────────────────────────────────┘
         │
         │ 管理
         ▼
┌──────────────────────────────────────────────────┐
│  子进程 1 (8081)         子进程 2 (8082)          │
│  ┌──────────────────┐  ┌──────────────────┐      │
│  │ FastAPI app      │  │ FastAPI app      │      │
│  │ 拓扑 A 的接口    │  │ 拓扑 B 的接口    │      │
│  │ GET /api/devices │  │ GET /api/alerts  │      │
│  │ POST /api/query  │  │ GET /api/health  │      │
│  └──────────────────┘  └──────────────────┘      │
└──────────────────────────────────────────────────┘
```

#### 核心模块

**文件**：`backend/app/core/instance_runner.py`（新建）

```python
class InstanceRunner:
    """管理 mock_instances 的子进程生命周期"""

    def __init__(self):
        self._processes: dict[str, subprocess.Popen] = {}  # inst_id -> process

    def sync_all(self):
        """从 DB 读取所有 enabled 实例，启动缺失的，停止多余的"""

    def start_instance(self, inst_id: str, port: int, topology_id: str):
        """启动子进程：uvicorn app.mock.instance_app:create_app(topology_id) --port X"""

    def stop_instance(self, inst_id: str):
        """终止子进程"""

    def restart_instance(self, inst_id: str):
        """停止后重新启动"""
```

**文件**：`backend/app/mock/instance_app.py`（新建）

每个子进程加载一个独立的 FastAPI app，仅注册指定拓扑下的接口：

```python
def create_app(topology_id: str) -> FastAPI:
    app = FastAPI()
    # 从 DB 读取该拓扑下的 api_configs
    # 注册 mock 路由（复用 handler.make_handler）
    return app
```

#### 生命周期

| 事件 | 行为 |
|------|------|
| 主进程启动 | `InstanceRunner.sync_all()` — 为所有 enabled 实例启动子进程 |
| 创建实例（enabled=true） | 自动启动子进程 |
| 创建实例（enabled=false） | 仅记录配置，不启动 |
| 编辑实例 port/topology | 重启子进程（新 port 新进程） |
| 切换 enabled（false→true） | 启动子进程 |
| 切换 enabled（true→false） | 终止子进程 |
| 删除实例 | 终止子进程 |
| 子进程崩溃 | 记录日志 + 自动重启（最多 3 次/分钟，超过则标记异常） |
| 主进程关闭 | 终止所有子进程 |

#### 路由隔离

每个子进程仅暴露其拓扑下的接口。主进程（8080）始终保留 Admin API + 所有接口的历史兼容行为。实例端口上**不暴露** `/admin/api/*` 管理端点。

**api_configs 按拓扑过滤**：

```python
conn.execute(
    "SELECT id, method, path FROM api_configs WHERE topology_id = ? AND enabled = 1",
    (topology_id,),
).fetchall()
```

#### InstanceRunner 触发时机

在 `main.py` 的 lifespan 中启动：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    mock_registry.bind(app)
    mock_registry.load_all()
    
    # 新增：启动实例进程管理器
    runner = InstanceRunner()
    runner.sync_all()
    
    yield
    
    # 关闭所有子进程
    runner.shutdown_all()
```

#### 实例状态展示

`mock_instances` 表新增 `status` 列：

| 值 | 含义 |
|------|------|
| `running` | 子进程正常运行 |
| `stopped` | enabled=false，未启动 |
| `error` | 子进程启动失败或反复崩溃 |
| `starting` | 正在启动中 |

前端实例页面"状态"列展示对应颜色的 Tag。

## 备选方案

| | 方案 A（推荐）：端口实例表 | 方案 B：仅 port 字段 | 方案 C：不分离实例 |
|---|---|---|---|
| 做法 | 新增 mock_instances 表 | api_configs 加 port 列 | 保持现状，不改 |
| 多端口共享接口组 | ✅ 实例下挂接口，一键管理 | ❌ 每个接口独立设 port | ❌ 不支持 |
| 实例级启停 | ✅ 一键禁用整个实例 | ❌ 需逐接口操作 | ❌ |
| 导入导出 | ✅ 按实例导出 | ⚠️ 按 port 筛选导出 | ❌ |
| 实施成本 | 中（新表 + 新页面） | 低（只加列） | 无 |

推荐方案 A，因为端口实例是接口管理的核心组织单位，值得独立建模。
