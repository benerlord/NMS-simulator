## 3. 详细任务分解

### 阶段 1: 项目基础设施

#### 任务 1.1: 后端项目初始化

**描述：** 搭建 Python 后端项目骨架，配置 uv、FastAPI、目录结构。

**工作内容：**
- 初始化 uv 项目，创建 `pyproject.toml`
- 安装核心依赖：`fastapi`、`uvicorn`、`aiosqlite`、`pydantic`、`pydantic-settings`、`loguru`、`apscheduler`
- 创建目录结构：`app/core/`、`app/api/`、`app/services/`、`app/protocols/`、`app/dal/`、`app/models/`
- 编写 `app/main.py` 入口，配置 FastAPI 生命周期
- 编写 `app/config.py`，使用 pydantic-settings 管理配置
- 配置 loguru 日志（按模块/级别分类）
- 配置 CORS 中间件

**验收标准：**
- [ ] `uv run python -m app.main` 启动成功，监听 8000 端口
- [ ] `GET /api/health` 返回 `{"status": "ok"}`
- [ ] 日志输出到控制台，格式包含时间、级别、模块
- [ ] 配置可通过环境变量或 `.env` 文件覆盖
- [ ] 项目目录结构与架构文档一致

### 阶段 2: 数据层

**描述：** 实现 SQLite 文件数据库的初始化、迁移、CRUD 封装。

**工作内容：**

- 实现 `schema_migrations` 迁移机制：版本检查 → 按序执行迁移 → 记录版本
- 配置 SQLite PRAGMA（WAL 模式、外键、缓存）
- 编写所有 12 张表的建表 SQL（与数据库设计文档一致）
- 插入预置数据：device_types（5 条）、protocol_configs（4 条）、session_config、snmp_trap_config、system_settings

**验收标准：**
- [ ] 首次启动自动创建 `./data/app.db` 并完成建表
- [ ] 再次启动不重复建表，预置数据不重复插入
- [ ] `schema_migrations` 表记录当前版本
- [ ] `PRAGMA journal_mode` 返回 `wal`
- [ ] `PRAGMA foreign_keys` 返回 `1`
- [ ] 可通过 SQLite 客户端查看所有表和预置数据

#### 任务 2.2: 内存查询引擎

**描述：** 实现 SQLite `:memory:` 内存库，创建虚拟表，提供数据同步和 SQL 执行接口。

**工作内容：**
- 实现 `MemoryStore`：管理 SQLite `:memory:` 连接
- 创建 5 张虚拟表（devices / ports / links / alarms / metrics），使用 camelCase 列名
- 实现 `full_sync(topology_data)`：清空所有表 → 批量 INSERT
- 实现 `sync_table(table_name, rows)`：单表全量同步
- 实现 `upsert_row(table_name, row)` / `delete_row(table_name, id)`：增量同步
- 实现 `execute_sql(sql, params)` → 返回列名 + 行数据
- 实现 `execute_count(sql, params)` → 返回总数
- 实现 `get_table_info()` → 返回各表列定义和行数

**验收标准：**
- [ ] 内存库启动后 5 张表创建成功
- [ ] `full_sync()` 可将 30,000 条设备数据同步到内存，耗时 < 500ms
- [ ] `execute_sql("SELECT * FROM devices WHERE type = :type", {":type": "switch"})` 返回正确结果
- [ ] `execute_sql` 支持 JOIN 查询：链路关联设备和端口的 DN
- [ ] `execute_count` 返回正确总数
- [ ] `get_table_info()` 返回每张表的列名、类型和当前行数
- [ ] 增量同步（upsert/delete）后查询结果立即更新

### 阶段 3: 拓扑管理后端

#### 任务 3.1: TopologyManager 服务

**描述：** 实现拓扑管理器核心服务——内存拓扑数据的 CRUD 和索引管理。

**工作内容：**
- 实现 `TopologyManager` 服务类
- 内存数据结构：devices / ports / links / alarms / metrics 列表
- 索引维护：byId / byDN / byDeviceId 三级索引
- 设备 CRUD：create / update / delete / get / list / batch_update / batch_delete
- 端口 CRUD：create / generate_ports / update / delete / batch_update
- 链路 CRUD：create / update / delete / batch_delete
- 链路创建/删除时自动更新端口状态（connected ↔ free）
- DN 自动生成：根据 dnTemplate 和设备/端口 ID 生成实际 DN
- 数据变更时触发 EventBus 事件
- 数据变更时调用 MemoryStore 增量同步

**验收标准：**
- [ ] 创建设备后，通过 `get_device(id)` 能取到，索引中能按 ID 和 DN 查找
- [ ] 创建设备并提供 portConfig 时，自动生成端口列表，端口 DN 正确
- [ ] `generate_ports(device_id, config)` 生成 N 个端口，名称和 DN 按模板生成
- [ ] 创建链路后，两端端口状态自动变为 `connected`
- [ ] 删除链路后，两端端口状态自动恢复为 `free`
- [ ] 删除设备时，关联的端口和链路一并删除
- [ ] 批量更新 100 个设备属性，耗时 < 100ms
- [ ] 每次数据变更都触发对应的 EventBus 事件
- [ ] 每次数据变更后，MemoryStore 中对应表数据同步更新

#### 任务 3.2: 告警与指标管理

**描述：** 在 TopologyManager 中实现告警和指标数据的管理。

**工作内容：**
- 告警 CRUD：create / update / delete / clear / batch_create / batch_delete
- 告警清除：设置 status=cleared + clearTime
- 指标 CRUD：create / update / batch_create / batch_delete
- 告警/指标变更时触发 EventBus 事件
- 告警/指标变更时同步到 MemoryStore

**验收标准：**
- [ ] 创建告警后，告警关联的 deviceId 对应的设备必须存在，否则返回错误
- [ ] 清除告警后，status 变为 `cleared`，clearTime 被设置
- [ ] 批量创建 1000 条告警，耗时 < 200ms
- [ ] 删除设备时，关联的告警和指标一并清理
- [ ] 告警创建时触发 `alarm.created` 事件
- [ ] 告警列表支持按 level / status / deviceId 筛选

---

#### 任务 3.3: 拓扑持久化与版本管理

**描述：** 实现拓扑的保存/加载/切换/版本回退功能。

**工作内容：**
- 手动保存：将 TopologyManager 内存数据序列化为 JSON → 写入 topologies 表 → 写入 topology_history 表 → 清理旧版本
- 加载拓扑：从数据库读取 → 反序列化 → 替换 TopologyManager 内存数据 → full_sync 到 MemoryStore
- 切换拓扑：保存当前拓扑 → 加载目标拓扑 → 更新 is_active 标记
- 版本回退：从 history 表读取指定版本数据 → 替换当前数据 → version+1 → 保存
- 自动保存：注册 APScheduler 定时任务（默认 60 秒），防抖保存通过 EventBus 事件触发

**验收标准：**
- [ ] 手动保存后，topologies.version + 1，updated_at 更新
- [ ] 手动保存后，topology_history 新增一条记录
- [ ] 加载拓扑后，TopologyManager 内存数据完整，MemoryStore 虚拟表数据正确
- [ ] 切换拓扑前自动保存当前拓扑
- [ ] 版本回退后，当前拓扑数据与历史版本一致，version 在当前基础上 + 1
- [ ] 历史版本数超过 max_versions 时，最旧的版本被自动清理
- [ ] 自动保存定时触发，日志中记录保存时间和版本号

---

#### 任务 3.4: 拓扑验证与自动布局

**描述：** 实现拓扑配置验证和自动布局计算。

**工作内容：**
- 验证规则：设备名称重复、DN 格式错误、端口溢出、孤立端口、链路端口不存在、必填字段缺失
- 验证结果：issues 列表，每项含 level / type / message / target / fixable / suggestion
- 一键修复：自动修复 fixable=true 的问题（重命名重复设备、删除孤立端口等）
- 自动布局算法：
  - 层次布局（hierarchical）：dagre 算法或手动实现分层
  - 力导向布局（force-directed）：简单弹簧模型
  - 圆形布局（circular）
  - 网格布局（grid）
- 布局输入：设备列表 + 链路列表 → 输出：节点位置映射

**验收标准：**
- [ ] 检测出设备名称重复，返回 `{type: "duplicate_name", fixable: true}`
- [ ] 检测出链路引用不存在的端口，返回 `{type: "invalid_port_ref", fixable: false}`
- [ ] 一键修复重复名称：自动追加后缀 `-2`、`-3`
- [ ] 层次布局：有连接关系的设备分层排列，无交叉
- [ ] 力导向布局：100 个节点在 500ms 内完成计算
- [ ] 网格布局：设备按行列均匀排列
- [ ] 布局结果返回 `{nodePositions: {dev_id: {x, y}}}`

#### 任务 6.4: QueryPipeline - SQL 模式

**描述：** 实现 SQL 数据源的查询管道——参数绑定、SQL 执行、自动分页。

**工作内容：**
- 实现 `QueryPipeline`：根据 dataSource.type 分发处理
- SQL 模式流程：
  1. 参数绑定：从 URL query params 提取参数 → 映射到 SQL 命名参数
  2. 未传参数设为 NULL（用于 `:param IS NULL OR` 模式）
  3. Count 查询：`SELECT COUNT(*) FROM ({用户SQL})`
  4. 分页追加：在用户 SQL 末尾追加 `LIMIT :pageSize OFFSET :offset`
  5. 执行分页查询
  6. 返回 items + total + pageNo + pageSize
- pagination.enabled=false 时不做 count 和分页追加
- SQL 执行通过 MemoryStore.execute_sql()

**验收标准：**
- [ ] `GET /api/devices?type=switch&pageNo=2&pageSize=50` 正确返回第 2 页的 switch 类型设备
- [ ] 未传 type 参数时，`:type IS NULL` 条件为 true，返回全部设备
- [ ] total 字段准确反映总记录数（不包含 LIMIT）
- [ ] 链路查询的 JOIN SQL 正确执行，返回关联的设备和端口 DN
- [ ] pagination.enabled=false 时返回全部数据，无 total / pageNo / pageSize
- [ ] SQL 语法错误时返回清晰的错误信息
- [ ] 参数绑定使用命名参数，防止 SQL 注入

## 5. 技术风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| AntV X6 大规模节点性能 | 3 万节点渲染卡顿 | 虚拟滚动 + 仅渲染可视区域节点 + 画布分层 |
| 40MB JSON 序列化/反序列化性能 | 保存/加载慢 | orjson 加速 + 流式解析 + 异步 IO |
| Mock Server 独立端口方案 | uvicorn 多实例管理复杂 | 考虑用 aiohttp 启动轻量 HTTP Server 替代 |
| SQLite 内存库并发写入 | 拓扑编辑和 Mock 查询竞争 | 写入用锁保护，读取不加锁（WAL 特性） |
| Monaco Editor 包体积大 | 前端首屏加载慢 | 按需加载（lazy import）+ CDN 引入 |
